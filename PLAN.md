# 381s-galleries — client galleries for 381 Studios (Pixieset alternative)

> Live at **https://gallery.381studios.ar/<slug>** · Repo: `PAumedes/381s-galleries`
> This file is the single source of truth for the build. Every contributor reads the sections it needs before starting a task.
> Work happens **one task at a time**: touch only the files listed for that task and stop when the acceptance criteria pass.

---

## 1. Goal

Deliver photos to clients through branded online galleries, at $0/month infrastructure cost (besides Google Drive storage).

- **All images** (every size) are exported by **Capture One** into a folder synced by **Google Drive for desktop**. No upload script, no image processing anywhere else.
- The app **only reads** Drive. It discovers galleries and photos by scanning a Drive folder.
- **App + API** run on **Cloudflare Workers**, data in **Cloudflare D1**, **R2** used only as a cache for preview images.
- No home server, no always-on machine.

## 3. Drive folder convention (the photographer's side)

```
My Drive/
└─ 381studios/                        ← root folder, ID stored in settings
   └─ name-of-the-album/              ← one folder = one gallery (folder name → slug; title editable in admin)
      ├─ high-res/                    ← 2048px long edge — required. "High-res" download + lightbox on large screens
      ├─ web/                         ← 1200px long edge — "Web" download + lightbox on phones
      ├─ ig/                          ← 1080px long edge — "Instagram" download
      ├─ thumb/                       ← 600px long edge — grid
      ├─ preview-wm/                  ← optional, 2048px with C1 watermark — what *proofing* galleries (Prueba) show instead of web/high-res
      └─ thumb-wm/                    ← optional, 600px with C1 watermark — grid thumbs of proofing galleries (else preview-wm is used, heavier)
```

- All recipes: JPEG, sRGB, made by Capture One. The app never resizes or re-encodes.
- **Sets:** optional subfolders with the same name inside each recipe folder (`high-res/Ceremonia/`, `web/Ceremonia/`…). Files at the recipe root go to set "Highlights".
- **Matching rule:** files match across recipe folders by **set + base filename without extension**. `high-res` is required. Fallbacks: `web` → `high-res`, `thumb` → `web` → `high-res`. `ig` is optional; if missing, the Instagram download option is hidden for that photo. `preview-wm` and `thumb-wm` optional (`thumb-wm` is never required and a missing one raises no issue).
- Mismatches (e.g. a file in `thumb` with no `high-res`) are listed in the admin gallery page, not silently dropped.
- Capture One: all recipes enabled in one export, output `…/381studios/[Session Name]/<recipe folder>`. One click produces everything.

## 5. Core flows

### 5.1 Sync (cron + button) — `app/lib/server/sync.ts`
1. List child folders of the root → upsert a `galleries` row per folder (new ones start as **draft**, slug = slugified folder name, title = folder name).
2. Change detection: Drive folder `modifiedTime` does NOT reflect changes deep inside it, so use the **Changes API**: keep a `drive_changes_token` in `settings`; if `listChanges(token)` reports nothing changed (and it's not a forced "Sync now"), stop. Otherwise rescan every non-archived gallery: list recipe folders and their set subfolders (paginate, request only `id,name,mimeType,size,modifiedTime,trashed,imageMediaMetadata(width,height,time,rotation)`; the contract's width/height are rotation-corrected). Store the new token only after a successful run.
3. Build photo records with the matching rule (§3; set names and base names match case-insensitively; a case-only set rename updates `set_name` in place, ids unchanged). Upsert. **No hard deletes on a single scan:** a photo whose high-res file is absent gets `photos.missing_since` (ISO) set; if it is present again the column is cleared; it is hard-deleted (with its R2 keys) only when `missing_since` is older than `SYNC_DELETE_GRACE_MS` (1 hour) on a later run (runs keep rescanning while any grace period is pending). If a gallery's high-res folder is missing or has zero JPEGs while the gallery has photos, nothing is marked or deleted and the gallery gets issue `highres_empty`.
4. Store mismatches in `sync_issues_json` (capped at 200 entries + a final `{"truncated": n}` summary); a new gallery with a `preview-wm` folder starts in `proofing` (else `delivery`); a rescan switches to `proofing` only when preview-wm files first appear and never back to `delivery` (an admin choice, and a proofing gallery that loses its files 404s instead of leaking clean images).
5. Stay within Worker limits (T1.3 decision): the scan is **breadth-first with `listChildrenMany`** (root → albums → all recipe folders → all set folders: ~4 queries for the whole library). `runSync` takes a `budget` (default 45; Workers Free allows 50 external subrequests) counting EVERY external call: `listChanges`, `getStartPageToken`, `getMeta(root)`, every scan query and the Google OAuth refresh (the drive factory counts it in `drive.subrequests()`). It checks that the next call fits BEFORE making it and re-checks after; on overrun it aborts with `SyncBudgetError` before any DB write and the changes token is not stored. D1/R2 calls are a separate pool (limit 1000): a counter aborts above 900. D1 writes are chunked into batches of <=100 statements per gallery (ordered so a failure mid-gallery leaves consistent rows; the next run re-diffs). A `sync_lock` settings row (5 min expiry) prevents overlapping runs. `listChanges` falls back to a full rescan only on 400/404 (stale token); other errors are rethrown.
6. **Archived on removal (with grace):** an album folder that disappears or is trashed first gets `galleries.folder_missing_since`; only after `SYNC_DELETE_GRACE_MS` is the gallery set to `archived` and its previous status stored in `archived_prev_status` (rows and photos are kept). The same step sets `archived_by_sync = 1`. If the folder returns, `folder_missing_since` is cleared and the previous status is restored **only for galleries with `archived_by_sync = 1`** (an admin-archived gallery, `archived_by_sync = 0`, stays archived); restoring clears `archived_by_sync`. If the root listing is empty while galleries exist, the run aborts (console error, no writes, token not stored, result `skipped: "empty_root"`). Renaming a folder never changes an existing gallery's slug/title/status.
7. **Mock auto-publish:** when `DRIVE_MODE=mock`, new galleries are created `published` (instead of `draft`) so the seeded galleries are viewable immediately.

### 5.2 Client views gallery
`/:slug` → PIN form if needed → cookie. Draft/expired/archived → "gallery unavailable" page. Justified grid of thumbs (using width/height), sets as tabs, lightbox showing `web` (or `preview-wm` in a proofing gallery, see 5.3), keyboard + swipe, preload next. Log one `gallery_views` row per session; skipped for HEAD, prefetch (`Purpose`/`Sec-Purpose`) and bot UAs, and cookieless views are deduped per (gallery, hashed IP) within 30 min. Unlock redirects to `/` + `encodeURIComponent(slug)` (+ `?lang=` if valid), never the raw pathname; missing `CF-Connecting-IP` is "local" in mock mode and otherwise null (`clientIpHash`): PIN/visitor endpoints answer 429, views are logged with `ip_hash` NULL (no dedupe bucket); unknown-slug POSTs share a per-IP limiter (pseudo-gallery `unknown`). The locked screen shows the gallery title (accepted studio choice). **Link previews (Open Graph, `galleryMeta` in `app/lib/og.ts`):** published, unexpired, no-PIN galleries emit og:type/site_name/title (gallery title)/description (`<localized date> · <studio>`)/url (`publicOrigin`+slug)/twitter:card, plus og:image = `${publicOrigin}/img/<coverId>/view-sm` (the preview-wm file in a proofing gallery, in which case the cover must have one, else no og:image; cookieless works for public galleries) with width/height at a 1200 long edge and alt = title. PIN, locked, unavailable and unknown galleries get generic meta (studio name only, no image, no title leak; locked == unavailable). Preview bots are never logged as views. **All client queries filter `photos.missing_since IS NULL`, via the shared `photoVisible` predicate (`app/db/index.ts`)** (photos in their sync grace period are hidden from clients).

### 5.3 Images route — `/img/:photoId/:variant` (`thumb` | `view-sm` | `view-lg`)
Check gallery cookie for that photo's gallery → try R2 `<photoId>/<variant>` → on miss, stream from Drive (`files/<id>?alt=media`), `tee()` the body into R2 and the response. `Cache-Control: private, max-age=600`, ETag/304. A blank/unparseable Drive Content-Length counts as absent (streamed uncached). Accepted: browsers may keep a stale image up to 10 min after a watermark toggle or re-export.
- `thumb` → thumb (fallbacks per §3)
- `view-sm` → web 1200 (lightbox on phones, via `srcset`/`sizes`)
- `view-lg` → high-res 2048 (lightbox on large/retina screens)
- **Gallery mode (T6.3), one switch "Modo" per gallery.** `delivery` (Entrega): every public image is clean (`thumb ?? web ?? high-res`, `web ?? high-res`, `high-res`), downloads per `allow_*`. `proofing` (Prueba): every public image is watermarked: cover and lightbox (`view-sm`/`view-lg`) = `preview-wm`; grid `thumb` = `thumb-wm ?? preview-wm`, NEVER a clean thumb; og:image = the `view-sm` of a photo with preview-wm, or none. A photo without preview-wm answers 404 on all three variants (the admin edit page lists it as issue "Falta preview-wm"). Admin previews (`/admin/img`) always show the clean files, and for proofing galleries bypass R2 (the keys are shared with the public watermarked objects).
- **Proofing is for picking favourites:** favourites work as usual; the client payload (`OpenGallery`) carries `mode` and has every `allow_*` false, so no download UI is rendered; `POST download-tokens` and `POST bulk` answer `403 {error:"proofing"}` (before the email gate); `/dl/:token` re-reads the mode and answers the generic 410 (tokens issued under delivery die at once; switching back revives still-unexpired ones). Image protection (deterrent, not DRM): `.img-protect` (`-webkit-touch-callout: none; user-select: none`) on the grid, lightbox and cover; `contextmenu` default-prevented there; `draggable=false`; a transparent overlay element above each grid tile, the lightbox photo and the cover, so "Save image" never targets the `<img>`. Keyboard/focus handling is unchanged (the overlay sits inside the tile's open button).
Cache rules (one paragraph): R2 objects carry `httpMetadata.contentType` and `customMetadata {fileId, wm: "0"|"1" (1 = proofing/watermarked file), v}` (server-side only, never in responses), where `v` is the resolved source file's Drive modifiedTime from `photos.variant_versions`. A hit is valid only if `fileId`, `wm` and `v` equal the current resolved file id, watermark flag and version; otherwise it is a miss and the object is overwritten, so re-exports and watermark toggles need no explicit invalidation (Drive for desktop overwrites in place and keeps the file id). Unknown `v` is never cached; only non-empty bodies (Content-Length > 0) are cached (length 0 → 502). Content-Type passes through if `image/jpeg|png|webp`, else `image/jpeg`.

**Cache warming (T6.2), `app/lib/server/warm.ts`:** the first view of a photo streams from Drive (0.5-2 s, and a grid of thumbs hits Drive rate limits), so a second cron `* * * * *` (free; the 15-minute one still syncs; `dispatchScheduled` in `scheduled.ts` picks by `controller.cron`, unknown crons sync) runs `warmBatch`. It selects visible photos of non-archived galleries (newest gallery first) whose expected `photos.cache_warm_key` differs from the stored one. The key is a SHA-256 prefix over `thumb` and `view-sm` of (resolved file id, watermark flag, modifiedTime), so re-exports and mode switches make photos stale again by themselves. In proofing it warms `thumb-wm` (or the `preview-wm` fallback) and `view-sm` (= preview-wm). Migration 0013 recreates the 0012 triggers: a `galleries.mode` change and any change of `drive_thumb_wm_id` reset the expected keys. For each, `fillCache(env, photo, variant, drive)` (shared with `/img`: same `resolveSource`, validity check and R2 `put`/`customMetadata`) writes `thumb` and `view-sm` only (never `view-lg`; an already valid R2 object costs no Drive call) and then the marker is updated; a failure leaves the marker so the next minute retries, and does not stop the batch. Budgets: 40 external subrequests per run (counted with `drive.subrequests()`, so retries and the OAuth refresh count; the next call must fit before it is made) and 900 CF-service ops. `runScheduledWarm`: does nothing in mock mode; skipped while `sync_lock` is held; takes a `warm_lock` setting (`<iso>|<uuid>`, 3 min expiry) so runs never overlap; after a scan that finds nothing stale it sets `warm_idle` (5 min), so idle minutes cost one settings read and no subrequests (a sync that changed anything clears it). Setup page shows "Fotos en caché: N / M" = visible photos whose marker is current / visible photos.

**Cover save warming (T6.15):** `warmCoverPhoto` warms only `thumb` and `view-sm` of the saved cover (what the editor shows next); `view-lg` is skipped because in Prueba it resolves to the same preview-wm file as `view-sm` (a second Drive fetch of identical bytes) and in Entrega it is the full-size original.

**Warming notes:** warming already runs only on change. Stale markers come from sync detecting new or modified files. R2 objects don't expire. The Prueba grid reuses `preview-wm` when no `thumb-wm` exists, and the app never generates images.

**Versioned URLs (T6.2):** every gallery photo carries `v` = `imageVersionToken(env, photo, proofing)`: HMAC-SHA256 (SESSION_SECRET) over what the three variants currently resolve to (file ids, wm flags, modifiedTimes), 16 hex chars, so Drive ids are not recoverable. The client appends `?v=<v>` to `/img` URLs (`imgUrl(id, variant, v)`). `/img` answers `Cache-Control: private, max-age=31536000, immutable` only when `?v=` equals the current token; missing or different `v` keeps `private, max-age=600`, so the old 10-minute staleness rule still covers un-versioned URLs (og:image, admin). Admin images (`/admin/img`) stay `private, no-store` unless the URL carries the matching admin token (`?v=`, `adminImageToken`: HMAC over the clean and watermarked thumb/view-sm file ids, flags and modifiedTimes; null when a version is unknown), in which case they are `private, max-age=31536000, immutable` (admin's own browser only; errors and the mock redirect are always `no-store`). Access checks run before any of this (a wrong `v` on a locked gallery is the same 404).

**Why no edge cache (Cloudflare Cache API / `cf` cache):** `/img` responses are private and access-checked per request (PIN session cookie, expiry, draft state, watermark policy). A shared edge cache would serve them to anyone who knows the URL, bypassing those checks; keying it by cookie defeats the purpose. R2 (same region as the Worker, no egress fee) plus long browser caching gives the speed without weakening access control.

R2 cache keys are exactly `<photoId>/thumb`, `<photoId>/view-sm` and `<photoId>/view-lg`. Image routes must not serve photos with `missing_since` set. When sync hard-deletes photos it removes those three keys per photo with ONE `CACHE.delete(keys[])` per <=1000 keys; on failure the ids stay in settings `r2_pending_deletes` (JSON, capped at 2000) and are retried first thing on the next run. The cron handler stores `sync_last_error` (`{at, message}`, generic text) for failures and for `no_root`/`empty_root` skips, and clears it on success; it rethrows so Cron shows the failure.

### 5.4 Email gate
If `require_email`, the first download or favorite opens an email (+ optional name) form → a `visitors` row (normalize email with trim + lowercase; the NOCASE index on (gallery_id, email) is a plain lookup index; shared regex in `app/lib/email.ts`) → visitor id in the cookie. **Visitors are per device, with no email verification:** `POST /visitor` never binds a session to a row created by another session (that would let anyone type a client's email and inherit their name and favourites). Each session gets its own row; if the session already has a visitor, its email/name are updated instead. The same email may therefore appear on several rows. Favourites are per device. Admin views (activity, favourites, CSV, "visitantes con email") group by `lower(email)`, so the same email on two devices shows as one person. Server gate: `requireVisitor` (`app/lib/server/access.ts`): `require_email && (no visitor || anonymous)` → `403 email_required`.
API (JSON, `Cache-Control: no-store`, cross-site POSTs rejected):
- `POST /api/g/:slug/visitor {email, name?}` → `{ok:true}` in every case (never a stored name/email); sets the session cookie when a row is created (rate limit scope `visitor:`).
- `GET /api/g/:slug/favorites` → `{visitor, favorites[]}`; `POST /api/g/:slug/favorites {photoId, on}` toggles one favourite (cap 2000 visible favourites; anonymous visitors, scope `anon:`, only when `require_email=0`).

### 5.5 Download
Client photo payload (`GalleryPhoto`) carries `variants: { web: boolean; ig: boolean }` (high-res is always present). **Downloads never fall back between sizes**: a missing web/ig makes that option unavailable (`unavailable[]` at issue time, 410 at `/dl`). The §3 viewing fallbacks are unchanged.
1. `POST /api/g/:slug/download-tokens {photoIds[1..50 unique], variant: "highres"|"web"|"ig", bulkId?}` (JSON, `no-store`): cross-site 403 → `openGallery` (404 parity) → body 400 → `requireVisitor` (`403 email_required`; anonymous visitors are created like favourites, scope `anon:`, when `require_email=0`) → variant flag else `403 variant_disabled` → `allow_bulk` required when >1 id or `bulkId` (`403 bulk_disabled`) → rate limit `dl:` 300/10 min (429 + `Retry-After`) → `{tokens: [{photoId, url: "/dl/<token>", filename}], missing[], unavailable[]}`. Ids not in this gallery / not `photoVisible` go to `missing`; photos lacking the variant to `unavailable`. `filename` = `<base_name>.jpg` | `-web.jpg` | `-ig.jpg` (path separators and control chars stripped, unicode kept). There is no per-token size: the bulk plan's `totalBytes` is the only byte figure. A `bulkId` must be a bulk row of this gallery (else 400).
2. Token: `signToken` with `DOWNLOAD_SECRET`, TTL 10 min, payload `{t:"dl", jti, g, p, v, vid, pf: pinFingerprint(pin_hash), b?: bulkId}`.
3. `GET|HEAD /dl/:token` → verify HMAC + expiry, reload the gallery: available, `pf` equals the current PIN fingerprint (a PIN change/clear revokes), photo `photoVisible` in that gallery, variant still allowed and present, and `allow_bulk` still on when the token has a bulk id `b`; so turning an `allow_*` flag off, or changing/clearing the PIN, revokes outstanding tokens at once; any failure (also bad/expired token) → the same generic `410`. Logs `INSERT OR IGNORE INTO downloads` keyed by `token_id = jti` (so retries/resumes log once; HEAD never logs; `kind` = bulk if `b`; country from `cf`, UA cut to 200). Google mode: `drive.streamFile(fileId, {range})` passthrough (Range → 206), `Content-Type` allowlisted (default `image/jpeg`), `Content-Length`/`Content-Range` from upstream, `Content-Disposition: attachment; filename="<ascii>"; filename*=UTF-8''<pct>`, `Cache-Control: private, no-store`, `nosniff`, `Referrer-Policy: no-referrer`. Mock mode: log, then 302 to `mockImageUrl(photo.id, variant, w, h)`. Drive 404 → 410, other errors → 502. Downloads always serve the **clean** files, never `preview-wm`. No buffering.
4. Access token: `app/lib/server/google-auth.ts#getAccessToken(env, {forceRefresh?})` refreshes from the stored refresh token, caches in `settings` until 5 min before expiry; on 401 refresh once and retry.

### 5.6 Download all / set
`POST /api/g/:slug/bulk {scope: "all"|"set"|"favorites", set?, variant}` (same gates, `allow_bulk` required, shares the `dl:` limit) inserts ONE `downloads` row (`kind=bulk`, `photo_id` NULL) and returns `{bulkId, photoIds (visible, gallery order, filtered by scope and by having the variant; favourites = the current visitor's), totalBytes? (high-res only)}`. Browser: request tokens in batches of 50 (passing `bulkId`) just in time → fetch each `/dl/<token>` → `client-zip` → `showSaveFilePicker` when available, else Blob fallback. Memory warnings (no picker only): always on iOS; on other browsers at an estimate above 1.5 GB (`estimateBytes`: per-photo average until the plan arrives, then the server's `totalBytes` for high-res, which can trigger a confirm after the plan). If the picker fails for a reason other than the visitor cancelling, a confirm ("continue in memory?", `download.pickerFailed`) precedes the Blob fallback. Scope choices: "set" is offered only while a set tab is active, "favorites" only if the visitor has favorites. 429s on token/bulk requests of a run are retried honouring `Retry-After` (capped at 60 s, at most 5 retries) instead of failing the run; a single-photo download fails fast. The per-photo rows come from the `/dl` hits; the single download clicks a plain anchor (no new tab; mock mode just navigates through the 302).

## 6. Security rules
- Never expose Drive file IDs, R2 keys or tokens to the client.
- Every client route checks the gallery cookie **and** that the photo belongs to that gallery **and** gallery is published + not expired.
- PIN: PBKDF2-SHA256 (Web Crypto), 100k iterations, random salt; max 5 attempts / 10 min per IP+gallery (IPv6 keyed on the /64) and 100 / 10 min per gallery across all IPs (`pinG:`; sessions already unlocked are never throttled and POST is a no-op redirect). Trade-off: a gallery-wide cap lets an attacker lock guests out for a window, but bounds brute force; with the 6-char minimum, 100 / 10 min means ~70 days worst case for a numeric 6-digit PIN (10^6 / 100 * 10 min), and a guest can still be locked out for up to 10 min under attack, via the shared `rateLimit` helper (`pin:` scope in `rate_limits`, §4). New PINs need >= 6 characters (older, shorter ones keep working).
- Security headers on every response (`workers/app.ts` -> `applySecurityHeaders`): CSP with a per-request nonce (`app/entry.server.tsx`), X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy.
- `/img` R2 misses: `img:<ipHash>:<gid>` 5000 / 10 min -> 429 before Drive is called.
- `SESSION_SECRET`, `DOWNLOAD_SECRET`, `TOKEN_KEY` must all differ (`assertDistinctSecrets`).
- Constant-time comparison for HMACs.
- Refresh token stored AES-GCM encrypted (`TOKEN_KEY`).
- Secrets only via `wrangler secret put` / `.dev.vars` (gitignored).
- **Privacy (owner decision):** raw IP addresses are NEVER stored, logged or exported: only `hashIp` (HMAC with `SESSION_SECRET`), used to count unique visits and detect abuse. Everything else we keep about a visit/download is listed in §4 (visitor-info columns) and disclosed on `/privacy` (es + en: what, why, "never your IP, only a one-way hash that differs per gallery", history is kept while the gallery exists, nothing deleted automatically; deleting the gallery deletes all of it, except the Drive folder id). Adding a column here means updating that page. Header and `request.cf` values are hostile: sanitised and capped by `visitorInfo`, CHECK-capped by the DB, CSV cells guarded against formula injection (`csvCell`: leading `= + - @ TAB CR`), and shown only to the admin (Actividad tab: location, device, browser/OS, referrer host, language per row, plus a top-5 summary of countries, devices, browsers and referrers per gallery; the CSV has the same columns). **Retention (owner decision): keep the data until someone removes the gallery; deleting a gallery deletes ALL data associated with it** (photos index, favourites, visitors, visits, downloads, rate-limit/PIN counters, cached R2 images), keeping only the Drive folder id in `ignored_folders` so sync does not re-create it. No automatic deletion otherwise; /privacy (es + en) says exactly this.
- **Deleting a gallery** (`deleteGallery`, `app/lib/server/gallery-delete.ts`; editor Datos tab "Eliminar galería" danger zone, intent `delete`, through `adminAction` then the slug typed by the admin is verified on the SERVER; success redirects to `/admin?deleted=1`; unknown or already-deleted gallery = 404). Order: (1) take the sync lock (running sync = refuse with a message, nothing deleted); (2) mark: archive + off the home page + tombstone (public routes 404, the warm cron and sync skip it, tokens in flight get 410); (3) R2 first: keys are `<photo id>/<thumb|view-sm|view-lg>` (images.ts), taken from the photo rows (hidden photos included), `CACHE.delete` in calls of <= 1000 keys, at most 25 calls per request (Workers Free: 50 subrequests); past that the cleaned photo rows are dropped and the admin sees "continuando…" and re-submits (resumable); (4) ONE atomic D1 batch deletes rate_limits (any key containing the gallery id, plus `dlj:<jti>` of its download tokens), favorites, downloads, gallery_views, visitors, photos and the gallery. Drive and the studio logo are not touched. A guard test introspects the migrated schema (any table with gallery_id / photo_id / visitor_id or an FK to galleries/photos/visitors must be in `GALLERY_TABLES` or `EXEMPT_TABLES` with a reason), and a seeding test checks gallery A is gone and B untouched in every table. **Review fixes:** (a) Ajustes never receives Drive ids: `ignoredFolders` are sent as `{handle, deletedAt}` where `handle = shortMac(SESSION_SECRET, 'ignored-folder:'+id)`; "Volver a incluir" posts the handle and the server resolves it (constant-time compare; unknown handle = "stale" message, nothing changes). (b) An R2/D1 failure while deleting returns `admin.msg.deleteFailed` (no 500); a half-deleted gallery stays in the admin list with a "Continuar eliminación" link to its editor, and re-submitting resumes (idempotent). (c) Under the same lock, ALL ids in `settings.r2_pending_deletes` (photos sync already removed, cache keys not yet cleaned; the list does not record the gallery, and they are orphans anyway) are deleted from R2 first and the list is cleared. Known limit: an `/img` fill or warm run already in flight when the gallery is marked can `put` an object after the R2 delete; it is an unreachable orphan (photo row gone, route 404s) and is not swept (no list calls). (d) "Volver a incluir" also clears `drive_changes_token`, so the next non-forced sync re-creates the gallery. (e) View inserts are conditional on the gallery row existing (`INSERT ... SELECT ... WHERE EXISTS`), so a view racing the delete leaves no orphan; download rows are not (a Drizzle insert after the gallery was loaded; the window is the same request, left as is). Privacy text says the Drive folder id AND the deletion date are kept.

## 11. Manual steps for the photographer
The step-by-step guide (Spanish) is **[DEPLOY.md](DEPLOY.md)** (§11 covers the `session.` → `gallery.` host change); it is the single source of truth for setup, the environment table (which values are secrets vs `wrangler.jsonc` vars), deploy order, Capture One recipes and troubleshooting. Deployment is entirely from GitHub Actions: the manual **Setup** workflow (`scripts/setup-cloudflare.mjs`: ensures D1/R2, writes `database_id`, deploys, then uploads secrets; generated secrets are never regenerated) and the **Deploy** workflow on push to main (both use the `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` GitHub secrets; CI on PRs only). `pnpm run deploy` applies the remote migrations, builds and deploys (`pnpm deploy` without `run` is a pnpm built-in); `pnpm secrets:check` verifies the required secrets exist and that `ALLOW_DEV_ADMIN` does not. `ALLOW_DEV_ADMIN` is local only (`.dev.vars`) and must never be set in production.

If sync hits Free plan CPU (10 ms) or subrequest limits on very large libraries, Workers Paid ($5/month) lifts them; the sync aborts cleanly rather than corrupting data.
